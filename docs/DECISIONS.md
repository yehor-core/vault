## Decisions required by the task

### Protection
- Where a second prompt is needed when enabling protection (browsers that don't return the PRF result at passkey creation)
- Whether more than one passkey can unlock a vault
- What to detect up front for browsers and authenticators that can't support passkey protection, and what to handle on failure

### Storage
- Position on requesting persistent storage (`navigator.storage.persist()`) — D-39
- How Vault behaves when it finds itself empty — D-11, D-12, D-40
- How a future storage format change would migrate — D-07, D-21

### Threat model — what to state explicitly
- Unprotected mode: exactly what protects keys against a copy of the browser profile or disk — D-04
- Records added or replaced: what can and cannot be detected, and when — D-05, D-06, D-14, D-15, D-18, D-20, D-34, D-35, D-36
- Older storage snapshot restored: what can and cannot be detected
- Malicious same-origin script while unlocked: what it can reach and how the API limits exposure — D-16 (partly: scopes are not isolation)
- Lost, deleted or replaced passkey: the outcome for protection and for passkey keys — D-59, D-61 (partly: passkey keys)
- Secrets in memory: the limits of what JS/WASM can promise — D-19 (partly: secp256k1)

### Platform
- TypeScript, or Rust compiled to WASM
- Where passkey features degrade per browser — D-51, D-56, D-62 (partly: passkey keys)
- Justification for every third-party cryptographic dependency — D-19, D-20, D-22

### Embedding
- Popup or iframe for other origins: choose and describe (do not build) — D-16, D-89

### Tests and scope
- How passkey paths were checked in engines where they can't be automated — D-62, D-86

## Decisions we make while building
D-03: Working docs stay out of git. docs/ (TASK.md, SPLIT.md, DECISIONS.md, prompts) stays out of git. DESIGN.md is self-contained: it states each decision's outcome and rejected alternatives itself; tracked files carry no links to DECISIONS.md and no decision IDs. Alternatives: track only docs/DECISIONS.md; move DECISIONS.md to the repo root. Why: keeps working notes, the task text and agent prompts out of the submitted repository. Given up: reviewers cannot see the full decision log, so DESIGN.md §10 must carry every alternative a reviewer would challenge. [Superseded by D-23.]
D-04: Key hierarchy. Every private key is sealed with ECIES to a vault wrapping key pair: ephemeral ECDH P-256 → HKDF-SHA-256 → AES-256-GCM, all WebCrypto. Unprotected mode: the wrapping private key is a non-extractable CryptoKey stored in the header record. Ephemeral public keys are stored and imported as SPKI. Enabling protection (S6) generates a fresh wrapping key pair and re-encrypts every key in the same transaction as the new header. Alternatives: X25519 ECIES with a non-extractable AES "device key" wrapping the X25519 private key, upgrade rewraps only the header (stable key pair); RSA-OAEP-3072 native wrapKey (label as AAD), rotated at upgrade; symmetric-only vault key (cannot add keys while locked). Why: adding a key needs only the public key, in both modes; no extractable secret is ever stored; rotation keeps keys added after protection safe from a pre-upgrade profile copy or storage-engine remnants. Probes: WebKit silently loses X25519 CryptoKeys stored in IndexedDB (record reads back null), so X25519 cannot be a stored root; WebKit accepts off-curve P-256 points in raw and JWK import but rejects them in SPKI. Given up: S6 upgrade is O(keys) and must redo on a concurrent add; a composed KEM/DEM instead of one native call; P-256 instead of X25519.
D-05: Key id = base64url(SHA-256(length-prefixed "vault/v1/key-id" ‖ scope ‖ type ‖ public identity)); public identity is the public key (S5 passkey: the credential id). Alternatives: crypto.randomUUID(). Why: an edited public key, type or scope is detected by list() without unlocking, in both modes; a passkey key gets the same id on every device. Given up: one SHA-256 per key on list(); 43-character ids.
D-06: AES-GCM associated data binds every stored field of the key record (format version, scope, id, type, public key, createdAt; S2 labels/metadata). After signing, Vault verifies the signature against the stored public key and fails with `corrupted` instead of returning it. Alternatives: AAD over identity fields only, labels editable but unauthenticated. Why: any edit to a key record fails closed when the key is used; a ciphertext replaced by an attacker-chosen key encrypted to the public wrapping key decrypts cleanly and is caught only by the verify. Given up: labels/metadata are immutable after generate; one extra verify per sign. [Narrowed by D-18: holds for key types with a sealed private key; passkey labels are not authenticated.]
D-07: Storage layout. One IndexedDB database (default name `vault`); IndexedDB schema version = storage format version = 1; store `meta` holds one `header` record; store `keys` is keyed by [scope, id]; every record carries v: 1 and any other value is rejected as `corrupted` (a legitimate newer format bumps the schema version first, so a v≠1 record inside a v1 database was not written by a Vault build). A database at a higher schema version fails open() with `incompatible`; open connections close on versionchange so a newer build is never blocked. Migration (described, not built): v2 bumps the schema version, makes structural changes in the upgrade callback and re-encrypts lazily per record, because the upgrade callback cannot await crypto. Alternatives: version only in the header. Why: per-record versions allow lazy crypto migrations; an old build never reads or writes a newer format. Given up: one field per record; two stores.
D-08: Writes are optimistic. All crypto runs before the transaction; one readwrite transaction over meta+keys re-reads the header, checks it is the one the ciphertext was made for (same wrapping public key), and writes, or aborts and redoes the whole operation (bounded, then `unavailable`). Alternatives: Web Locks held across read → crypto → write. Why: Firefox and WebKit end a transaction at the first non-IndexedDB await (probe; Chromium does not), so crypto cannot run inside one; IndexedDB alone gives atomicity and cross-tab serialization; no lock is ever held across a passkey prompt. Given up: crypto is wasted on a conflict. [Updated by D-61: a passkey key write is never redone; it commits into the vault as it is.]
D-09: Public API. `Vault.open({ name? })`; `generate(type) → KeyInfo`, `list() → KeyInfo[]`, `sign(id, data) → Signature`, `delete(id)`, `wipe()`, `close()`. `KeyInfo = { id, type, publicKey, createdAt }`. `Signature` is a union discriminated by `type`, starting with `{ type: 'ed25519', bytes }`. S1 works on the fixed scope 'default'; S2 decides how named scopes are exposed. Alternatives: sign returns a bare Uint8Array (breaks for passkey assertions in S5); key handles with methods (stale across tabs, larger surface). Why: a passkey assertion becomes one more union member without changing sign(). Given up: callers narrow on `signature.type`. [`sign(id, data)` superseded by D-17.]
D-10: Errors. One `VaultError` class with `code`: 'unavailable' | 'corrupted' | 'incompatible' | 'not-found' (later 'cancelled' in S5, 'locked' and 'unsupported' in S6) and `retryable` (true only for 'unavailable'); the original error is kept as `cause`. 'incompatible' = written by a newer format (reload a newer build), distinct from 'corrupted' (do not retry). Alternatives: one subclass per category. Why: exhaustive switch, one export, codes survive a postMessage boundary. Given up: no instanceof per category. [Updated by D-59: 'cancelled' and 'unsupported' both arrive in S5.]
D-11: Lifecycle. open() only opens the database; the header is created inside the first write if absent, so concurrent first setups converge on one header. wipe() clears both stores in one transaction and leaves an empty vault usable by every instance; a write prepared against a wiped header fails its header check (D-08) and is redone. Alternatives: eager header creation in open(); wipe closes every instance (terminal "wiped" state). Why: reads never write; one rule for wipe everywhere. Given up: "wiped", "never used" and "evicted" are the same state. [Updated by D-94: open() opens the database and reads the header; it never writes.]
D-12: Key records without a header are corrupted. If the `keys` store holds any record but `meta/header` is absent, list(), generate() and sign() fail with `corrupted`; only wipe() works. A header key present with an undefined value is also `corrupted`. Refines D-11: "empty" means no header and no keys. Alternatives: fail only generate() and sign() and keep listing the keys; keep creating a fresh header next to orphaned keys (rejected: a deleted protected header would become an unprotected vault, breaking "a protected vault never falls back to unprotected after a deleted record"). Why: no legitimate path produces keys without a header (the first generate is atomic, wipe clears both stores), so this state is tampering; failing closed now gives S6's no-downgrade for a deleted header. Given up: a writer who deletes only the header makes the vault unusable until wipe(); list() reads one more record.
D-13: Transient key-generation failures are retried. WebKit 27.2 (Playwright, Linux) rejects about 0.7% of generateKey('Ed25519') calls with OperationError (no successful key had a leading zero byte; Chromium and Firefox never fail). ed25519.generate retries up to 5 times on OperationError; a final failure is VaultError 'unavailable', whose meaning widens to "IndexedDB or WebCrypto failed in a way a retry may fix". Alternatives: no retry, classify as 'unavailable' and let every caller retry. Why: key generation has no side effects; five failures in a row are about 10⁻¹¹; tests and the demo become deterministic. Given up: an engine-bug workaround in the key type; 'unavailable' covers crypto as well as storage. Not checked: Safari on macOS.
D-14: WebKit tab crash on Ed25519 verify is documented, not prevented. In WebKit 27.2, crypto.subtle.verify('Ed25519') with some public keys (identity point, small y, top 16 bytes zero) kills the page's content process; import does not reject them in any format. A storage writer can plant a self-consistent record with such a key; sign() of it crashes the tab. Stated as "not protected" (WebKit only, denial of service by a storage writer, only when the app signs with an injected key); the test runs in Chromium and Firefox and is skipped in WebKit. Alternatives: verify with @noble/curves ed25519 (extends D-01 beyond secp256k1); compare the stored public key with one derived from the decrypted private key via JWK export (private key bytes in JS memory on every sign). Why: a storage writer can already destroy the vault; no new dependency; legitimate keys never trigger it. Given up: a known WebKit tab crash on injected keys. [Superseded by D-20.]
D-15: Field types are validated in S1 and the canonical encoding is typed. parseKeyRecord and parseHeader check every field's runtime type (byte fields are Uint8Array, createdAt a safe integer, scope and id strings, public key length per key type, IV 12 bytes, header root a CryptoKey) and fail with `corrupted`. encode() writes each part as type tag ‖ 4-byte length ‖ bytes: strings UTF-8, bytes only Uint8Array, integers only safe non-negative as 8-byte big-endian; anything else throws. The format version and createdAt enter the AAD as integers, not String(). Alternatives: leave type checks to S3 and narrow S1's claims; keep String() for numbers. Why: String() and an untyped encode() let a writer change a field's type without changing its id or AAD (createdAt "123" for 123, publicKey as Array or Int8Array), which sign() accepted; two independent guards close it. Given up: part of S3's "record validation" moves into S1.
D-16: Scopes. `vault.scope(name)` returns a `Scope` { name, generate, list, sign, delete }; `Vault` keeps open, scope, wipe, close (later: protection in S6, vault-wide events in S4). All scopes share one connection, header, wrapping key, protection state and unlock. `scope()` is synchronous and does no I/O; a Scope never exposes its Vault. Scope names are well-formed strings of 1–1024 UTF-16 code units (any origin fits), else TypeError. Scopes are namespaces, not isolation: any same-origin code can open any scope; isolating other-origin consumers is the embedding layer's job, which derives the scope from the message origin. Alternatives: a scope option on every call, defaulting to 'default'; one scope per Vault.open() (rejected: each instance would need its own unlock in S6, or a hidden global). Why: one unlock serves every key; a key operation without a scope cannot be written; code handed only a Scope cannot wipe. Given up: two classes; wipe and protection are vault-wide.
D-17: `sign` and `delete` take a KeyInfo: `sign<K extends KeyInfo>(key: K, data) → Signature<K['type']>`, `delete(key)`. KeyInfo is a union discriminated by `type`, derived from the registry, and carries `scope`. Vault takes only scope and type from the argument (S5: also what the prompt needs, so it starts before any I/O) and re-reads the record by id; a KeyInfo of another scope, or whose type differs from the stored record, is a TypeError; a missing id is `not-found`. Supersedes `sign(id, data)` in D-09. Alternatives: keep sign(id) and let S5 add an in-memory key directory (changes D-11) or a passkey-only method; passkey ids that carry the credential id (reopens D-05). Why: with opaque hashed ids (D-05), sign(id) cannot tell a passkey without an IndexedDB read first, which breaks the gesture rule; S2 changes the surface anyway; the signature type follows the key type. Given up: a caller who kept only an id calls list() first. Open for S6: unlock() has the same read-before-prompt problem. [Updated by D-73: unlock prompts with a fixed PRF input and no allowCredentials, and reads the header after the prompt.]
D-18: Labels. `generate(type, { label })`; `KeyInfo.label?: string`. A label is a well-formed string of 1–256 UTF-16 code units, else TypeError at generate and `corrupted` at read; immutable (D-06). Stored only when given (never `label: undefined`), and bound into the AAD only when present, as the tagged parts 'label', label after the v1 fields, so unlabelled records keep their v1 AAD and the v1 KATs. Not checked by list(); for key types with a sealed private key an edit fails sign() with `corrupted`. Passkey keys (S5) have no ciphertext, so their labels will not be authenticated. A storage writer can add a key with any label, so label spoofing is not prevented; callers that need assurance pin key ids. Alternatives: label plus JSON metadata stored as its exact text; labels outside the AAD for every type (renamable later, never authenticated). Why: the task asks for "label or metadata"; least code; edits are detected wherever a secret exists. Given up: structured metadata; renaming a key.
D-19: secp256k1: ECDSA over SHA-256(data), low-S, 64-byte r‖s (IEEE P1363), RFC 6979 deterministic nonces. Public key: 33-byte compressed SEC1, checked to be a valid curve point by list(). Private key: the raw 32-byte scalar, sealed with AES-GCM `encrypt` under the record cipher, and required to be exactly 32 bytes and a valid scalar after decryption (else `corrupted`). Key generation, signing and verification use @noble/curves (D-22) with every option passed explicitly. Verify-after-sign as for ed25519 (D-06). The type name 'secp256k1' names exactly this scheme; another scheme on the curve becomes a new type name. Alternatives: ECDSA over a caller-supplied 32-byte digest plus a recovery id; BIP-340 Schnorr. Why: same shape as ed25519 (signs the message); verifiable with OpenSSL; verify-after-sign withholds a faulted signature, which is what hedged nonces defend against, and determinism allows known-answer tests. Given up: not directly usable where a protocol fixes the digest (Ethereum keccak, Bitcoin sha256d) or needs a recovery id; the private key exists as JS bytes during generate and sign (Vault zeroes the buffers it owns; noble's internal copies are not zeroed).
D-20: ed25519 signatures are verified with @noble/curves ed25519 in strict RFC 8032 mode (zip215: false, which also rejects small-order public keys); signing stays in WebCrypto, so the private key is never JS bytes. list() checks a stored ed25519 public key with the same strict decoding. Supersedes D-14, whose premise "no new dependency" no longer holds after D-19; widens D-01 beyond secp256k1 for verification. Alternatives: keep WebCrypto verify and the documented WebKit tab crash. Why: noble's verify is pure JS and never reaches WebKit's crashing crypto.subtle.verify, so a planted degenerate key fails closed with `corrupted` in all three engines; verification handles only public data. Given up: native-only ed25519; noble's ed25519 and SHA-512 code in the bundle.
D-21: Storage format policy for key types. Until release, format v1 stays open: S2 adds the secp256k1 type and the optional label field to v1; existing records stay byte-identical and the v1 KATs keep passing; later slices extend v1 the same way. After release a new key type needs no version bump: a record whose type is a well-formed name (lowercase letters, digits, hyphens; at most 32 characters) that this build does not know fails with `incompatible` (reload a newer build); a malformed type stays `corrupted`. The type is checked before the rest of the record, so a newer type with different fields reads as `incompatible`, not `corrupted`. Alternatives: bump the schema version for every new key type (every older build then fails open() on every vault, and the core changes for each type). Why: adding a key type stays a local change. Given up: a record planted with a made-up type name reads as `incompatible`, not `corrupted` (it still fails closed).

A declined prompt (`NotAllowedError`): Vault reads the header again; if it no longer names that id, `not-found`, else `cancelled` (D-59). A malformed header: `open()` still succeeds, so `wipe()` stays reachable, and `unlock()` fails with `corrupted` without a prompt. No header format change. Alternatives: a second `get()` in `unlock()` when the discoverable one returns no PRF result; a discoverable second `get()` in `protect()`; record the failure only (D-92). Why: Firefox with a security key without `hmac-secret-mc` returns a PRF result to a `get()` with `allowCredentials` and none to a discoverable one (#108), so `protect()` succeeded and every `unlock()` then failed with `unsupported`, a protected vault that can't be used; with one request shape, a `protect()` that succeeds means `unlock()` gets a PRF result; TASK "Unlocking takes at most one passkey prompt." rules out a second `get()`; a discoverable `get()` in `protect()` would refuse that pair; D-73's "a kept credential id goes stale when another context protects or wipes" is answered by refreshing the id on every header read, not on notifications: an application shows Unlock after `state()`, so the id is fresh at the click, and a stale id costs one extra `unlock()` in a cross-tab race (`not-found`, then a refreshed id), never a changed vault, since the check after the prompt stays; the vault is local, so its unlock passkey is always named in this device's header and there is no fresh-device case. Given up: a cache and three edge-case rules; `open()` reads the header (D-11). Supersedes D-73, whose "Given up" (the picker lists every passkey of the site) goes away.

D-96: A chained second prompt waits for page focus. Before the second `get()` of `add` (D-56) and of `protect()` without a PRF result at creation (D-74), one shared function checks `document.hasFocus()`: true, it calls `get()` at once, with no await before it; false, it waits for the window's `focus` event, at most 2 seconds, then calls `get()`. No focus by then: `unavailable`, retryable, without a second `get()`. A `NotAllowedError` from that `get()` while `document.hasFocus()` is false: `unavailable`; with focus it stays `cancelled` (D-59). The first prompt of every operation is unchanged; no failure writes anything. Alternatives: only reclassify the `NotAllowedError`; record the pair as a limitation (D-92); a new error code; wait without a bound. Why: Safari 27.2 with a security key gives the page its focus back about 575 ms after the first prompt closes and refuses an earlier `get()` with `NotAllowedError` "The document is not focused." (#111), which Vault reported as `cancelled`, a cancel the user never made, so the pair could neither add nor protect; a top-level `get()` needs no user activation in any engine (docs/research/webauthn-passkey-keys.md §8), and the manual check in #111 opened the second prompt after `focus` with no new click; reclassifying alone leaves the pair broken; by D-92 a misclassified error is Vault's fault; a new code changes the API for one case, and `unavailable` is the retryable one: a retry from a click is expected to work; without a bound an `add` could hang; 2 seconds is about 3.5 times the 575 ms measured. Given up: a page that never regains focus learns it only after 2 seconds; a user who declines the second prompt while the page has no focus gets `unavailable`, retryable, not `cancelled`, as no engine tells that decline from the refusal; whether a browser other than Safari 27.2 reports `document.hasFocus()` false after a prompt it then answers is unconfirmed.
